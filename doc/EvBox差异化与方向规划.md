# EvBox 差异化与方向规划（工具选型 / 产品模式 / 特长打造）

> 日期：2026-09-26
> 依据：本项目实测源码（`src/`、`manifest.json`、`storage-tables.js`）+ 参考工程 `reference/class-schedule/docs/` 的 265 篇分析文档（表盘能力、渠道分发、插件生态、包体积、后台运行、商业化）。
> 目的：回答三个问题 —— **① 我们该做什么工具？② 该走"大而全"还是"工具市场/安装卸载"？③ 怎么做出不像现在这样平淡的特长？**

---

## 0. 一句话结论

> **主线走"精品单品 + 腕上提醒"（把倒数日做成纪念日管家），外壳用"预置式工具市场"包装安装/卸载体验，二期用 AstroBox 插件补上"手机填、手环看"的双端协同作为护城河。**
>
> **明确不做**：大而全的工具合集、真正的热插拔插件市场（平台不支持）、计算器/换算这类"手机更好用"的通用工具。

---

## 一、为什么现在"感觉平淡"——六条根因诊断

| # | 根因 | 具体表现（现状事实） | 后果 |
|---|------|----------------------|------|
| 1 | **品类天花板**：工具 = 低频 × 无数据 × 可替代 | 首页宫格是 `index.ux` 里硬编码的 5 条 `TOOLS`（倒数日/二维码/震动/数据备份/设备信息） | 无权重、无排序、无增长空间；用户"打开即用完" |
| 2 | **没用上手腕的特有能力** | 震动只当"震动实验室"的调试素材，抬腕/随时可见/触感提醒完全没被产品化 | 同样的功能出现在手机上体验更好 → 用户在腕上没有理由留下它 |
| 3 | **没有复访理由（无数据资产）** | 现有工具几乎不产生"明天还想看"的数据；`pinned_pages` 钉首页只被用来钉首页本身 | 次周留存趋近一次性使用 |
| 4 | **开发工具占用心智** | `tools.ux` 里"设备信息/设备ID诊断/黑屏检测"是开发者自用项，和用户工具混在一个列表 | 用户看到的第一个列表就是"看不懂的东西"，专业感被打折 |
| 5 | **没有分发与运营抓手** | 无渠道包统计（参考工程有 14 个渠道包 + 激活二维码 `&c=渠道码`）、无社区触点 | 发版即结束，做得好也没人知道 |
| 6 | **超能力被主动放弃** | 为瘦身移除了 `@system.interconnect`（`README.md` 第三节），而参考工程实测：**补上手机端批量导入后，竞争力 2.4 → 4.6 / 5** | 放弃了唯一能绕开"腕上输入难"的通道 |

**结论**：平淡不是因为"工具太少"，而是因为**没有一个"只有手环能给"的理由**。方向不是加工具，而是换支点。

## 二、平台能力边界（先划死路，避免规划幻觉）

| 能力 | 实测结论 | 对规划的硬约束 |
|------|---------|---------------|
| **表盘** | 快应用**不能生成/替换表盘**；表盘是独立 `.bin`，数据源白名单只有时间/健康/设备/环境，读不到快应用数据，且无存储、无输入法 | ❌ 表盘组件化、表盘读倒数日 = 死路。别在 roadmap 里留幻想 |
| **卡片 / 负一屏小组件** | 参考文档未涉及，无 API 迹象 | ❌ 不作为规划前提 |
| **动态加载代码（热插拔）** | `aiot-toolkit` 产出 `.rpk` + JSC 字节码，代码为静态 `require`，无 ESM 运行时解析 | ❌ "下载安装新工具"= 技术不可行；只能"包内预置 + 开关" |
| **官方应用商店分发** | 无低门槛 `.rpk` 通道；Vela 上架需商务对接，小米手表应用需 `.apk`+软著+备案 | ❌ 不能把"上架商店"当增长前提 |
| **实际分发渠道** | 米坛社区（按机型 12 个渠道位）、轻腕社区、GitHub Release；安装靠 **AstroBox 推送 `.rpk`** | ✅ 增长抓手 = 社区运营 + AstroBox + 渠道包统计 |
| **AstroBox 插件** | 插件（Rust→WASM，`.abp`）经蓝牙 + Protobuf 走 `interconnect` 与手环通信，能**读写设备数据、推送 rpk/表盘** | ✅ **唯一可扩展的"平台"入口**（二期护城河） |
| **后台提醒** | `@system.resident` 可用，但参考工程为**强制常驻**（耗电大）；提醒靠 `setInterval` + `vibrator('long')`；部分设备（RedmiWatch6/HyperOS3）需真机验证 | ⚠️ 提醒类工具必须做"**低耗电提醒策略**"，不能无脑常驻 |
| **包体积** | 参考工程 release rpk 809KB，`pages/` 占 **81%**，中文输入法单页 233KB | ⚠️ "大而全"会把包撑爆；每加一个页面都要算账 |
| **单帧渲染** | 单帧 **200+ 节点会触发看门狗复位**，参考工程靠分帧挂载降到约 70 节点 | ⚠️ 富交互工具（月历、图表）必须分帧 |
| **时间与网络** | 无精确计时 API；`system.request` 已声明但工具箱不该依赖网络 | ⚠️ 离线优先，计时"能看个大概"要诚实设计 |

**死路清单**：表盘联动、卡片组件、真·热插拔、商店上架、云同步（无账号体系）。

## 三、五种产品模式对比（核心章节）

| 模式 | 一句话 | 成本 | 风险 | 适配度 | 结论 |
|------|--------|------|------|--------|------|
| **M1 大而全** | 二十个小工具塞满首页宫格 | 高（每页 200-400 行 UI + 4 种屏型适配） | 高：包体积膨胀、首页失控、无复访 | ⚠️ 低 | **不做**。参考工程已证明"做了没人用"（滑动删除、T9 九键、Demo 页占包 39%） |
| **M2 精品单品** | 只把 1-2 个工具做到 90 分 | 低（已有倒数日底座） | 低 | ✅ 高 | **主线**。传播靠单品口碑，不靠数量 |
| **M3-A 预置式工具市场** | 包内预置全部工具，市场页做"安装/停用/彻底卸载" | 低（1 页 + storage 注册表） | 低（本质是 UX） | ✅ 高 | **推荐做外壳**（详见第六章）；但必须诚实：不产生新能力 |
| **M3-B 真·插件市场** | 手机端 AstroBox 插件市集，手环只留通用容器 | 高（协议 + Rust/WASM 插件 + 双端调试） | 中高 | ⏳ 二期 | **作为护城河备选**，先用手环侧协议验证价值 |
| **M4 双端协同** | 手机填、手环看/提醒（interconnect） | 中（协议已有原型，需恢复通道） | 中（耗电、部分机型不支持） | ✅ 高 | **二期核心**：正面解决"腕上输入难"这个品类死穴 |
| **M5 数据仪表盘** | 各工具数据汇到"我的一天"首页 | 中（首页重构 + 数据契约） | 低 | ✅ 中高 | **随 M2 自然生长**，不要一开始就搭 |

### 推荐组合（不做单选题）

```
M2 精品单品（支点：纪念日/提醒）
  ├── M5 数据仪表盘（首页形态：今天 + 倒数 + 待办提醒）
  ├── M3-A 预置式工具市场（体验外壳：像平台、能运营）
  └── M4 双端协同（二期护城河：手机填 / 手环提醒）
```

**为什么不是 M1**：工具箱的敌人不是"工具不够多"，而是"没有一个非用不可"。20 个小工具的用户价值 < 1 个每天都看的工具。

## 四、工具选型：该做什么、不该做什么

**评分模型**（5 分制，加权）：复访频次 30% ｜ 腕上独有价值 25% ｜ 数据沉淀 20% ｜ 实现成本低 15% ｜ 变现可能 10%。

**判据（三条同时看）**：① 需要"抬腕随时可见"或"触感提醒"？② 需要"到点发生"？③ 会积累可回看的数据？
→ 三条都不满足 = 手机上一定有更好的替代品 = **不该做**。

| 工具 | 复访 | 腕上独有 | 数据沉淀 | 成本低 | 变现 | 总分 | 判定 |
|------|:---:|:---:|:---:|:---:|:---:|:---:|------|
| **倒数日 → 纪念日管家** | 4 | 4 | 5 | 5 | 4 | **87** | 🥇 第一支点（已有底座，差"90 分"那 10%） |
| **喝水 / 久坐 / 用药提醒** | 5 | 5 | 3 | 3 | 4 | **84** | 🥇 第二支点（触感提醒 = 只有手环能给） |
| **经期 / 生理记录** | 4 | 5 | 5 | 2 | 4 | **83** | 🥈 高价值但隐私与算法要谨慎 |
| 习惯打卡（连续天数） | 4 | 4 | 5 | 3 | 3 | **79** | 🥈 与倒数日共用"日期+提醒"内核，边际成本低 |
| 极简记账 | 4 | 3 | 5 | 2 | 3 | **71** | 🥉 数据价值高，输入成本高 → 需 M4 配合 |
| 体重 / 体征记录 | 3 | 4 | 5 | 2 | 3 | **70** | 🥉 手环系统已有健康数据，需找差异化角度 |
| 数据备份 / 迁移（基建） | 2 | 3 | 4 | 5 | 4 | **66** | ✅ 继续做强（信任基础，高级版锚点） |
| 番茄钟 / 专注 | 3 | 5 | 2 | 4 | 2 | **67** | ⭕ 震动 + 常亮有价值，但无数据沉淀 |
| 密码 / 卡号备忘 | 3 | 4 | 4 | 2 | 2 | **64** | ⭕ 隐私成本高（本地明文存储风险） |
| 便签 / 日记 | 3 | 3 | 4 | 2 | 2 | **59** | ⭕ 中文输入法单页 233KB，投入产出比低 |
| 农历 / 节假日查询 | 3 | 3 | 2 | 3 | 2 | **54** | ⭕ 只作为倒数日的子能力 |
| 二维码生成（已有） | 2 | 2 | 3 | 5 | 2 | **53** | ✅ 保留但不投入 |
| 骰子 / 抽签 / 随机数 | 2 | 3 | 1 | 4 | 1 | **45** | ❌ 一次性娱乐，别做 |
| 秒表 / 计时器 | 2 | 3 | 1 | 3 | 1 | **42** | ❌ 无精确计时 API，体验注定差 |
| 计算器 / 单位换算 / 汇率 | 2 | 1 | 1 | 3 | 1 | **32** | ❌ 手机上更好用；腕上属"为了凑数" |

**第二梯队共同点**：它们共享同一个内核 —— **「日期/时间 + 本地提醒 + 一条记录」**。所以不要按"工具"拆，按**内核 + 模板**拆：

```
内核：Item = { id, title, date|schedule, repeat, remind, note, tags }
模板：纪念日 / 生日 / 打卡 / 用药 / 经期 / 喝水
```
一个内核 + N 个模板 = 5 个"工具"，包体积几乎不增，这才是腕上工具箱该有的架构。

## 五、把 1 个工具做到 90 分：以「倒数日」为例

**现状（P0 缺口）**：只有「名称 + YYYY-MM-DD + 顺/倒天数」，且名称输入刚接入中文输入法；无农历、无重复、无提醒、无导入导出、无样式可选。

| 优先级 | 能力 | 为什么值 90 分 |
|--------|------|---------------|
| P0 | **农历/公历双轨** + 农历节日 | 生日、忌日、传统节日全是农历；计算型展示，可纯离线 |
| P0 | **重复规则**（每年 / 每月 / 每周 / 一次性） | 生日自动推到下一次；解决"过完就作废"的致命体验 |
| P0 | **提醒**（提前 N 天 + 当天震动） | 把"看"变成"被提醒"——腕上唯一不可替代的东西 |
| P0 | **钉首页 / 大数字样式** | 抬腕即见天数，是产品的"脸" |
| P1 | **月历视图**（点日期添加） | 替代手输日期；顺带解决日期输入的痛点 |
| P1 | **导入导出**（二维码 / 文本码，复用 `lib/qrcode.js`） | 换机迁移 + 社交传播（发码给朋友 = 天然拉新） |
| P1 | **多显示模板**（大数字 / 圆环进度 / 卡片列表） | 复用 `homepage_template` 机制，用户可挑选 |
| P2 | **分组与标签**（家人 / 工作 / 健康） | 数据多了之后的组织能力 |
| P2 | **统计**（本月/本年事件数、坚持天数） | 数据沉淀的可视化，提高回访 |
| P2 | **分享**（生成分享图/码） | 社区运营素材 |

**提醒的技术方案（必须想清楚，否则耗电）**：
1. **不做**无脑常驻轮询；
2. 采用「**事件窗口唤醒**」：只在提醒日附近使用 `@system.resident` + 粗粒度定时器，其余时间不常驻；
3. 兜底「**打开补偿**」：每次启动检查错过的提醒并补震动/补提示条——这样即使系统杀掉后台，用户也不会漏（代价是提醒可能延迟到下次抬腕）；
4. 在设置里明确告诉用户"提醒精度取决于系统后台策略"，**诚实 > 假装**。

## 六、"安装 / 卸载"到底该怎么做（可落地设计）

**技术事实**：`.rpk` 静态编译 + JSC 字节码 → **无法运行时下载安装新工具**。所以"工具市场"只能做**预置式**：

### 6.1 数据模型

```js
// storage key: tool_registry
[{
  id: "countdown",            // 稳定 ID
  name: "纪念日",
  icon: "倒",
  uri: "/pages/countdown-manage",
  group: "时间提醒",
  enabled: true,              // 是否"已安装"（停用则从首页/列表消失，数据保留）
  pinnedHome: true,           // 与 pinned_pages 语义合并
  order: 0,                   // 首页排序
  installedAt: 1690000000000
}]
```

### 6.2 页面与交互

- 新增 `pages/tool-market`：三段式「已安装 / 可安装 / 已停用」，每项右侧「安装 / 停用 / 卸载」。
- **卸载两种语义必须分开**，否则用户会怕（也避免误删数据）：
  - **停用**：从首页与工具列表移除，**数据保留**，可一键恢复；
  - **彻底卸载**：清空该工具的 storage key，红色二次确认。
- 首页宫格从硬编码 `TOOLS` 改为**读注册表**（按 `order` 排序），把"钉首页"从"钉页面"升级为"钉工具"。
- 收益：首页永远干净（只放用户真正用的）、能按人群做推荐位、有"平台感"；成本 ≈ 1 个页面 + 1 处首页改造。

### 6.3 必须诚实的两点

1. 停用/卸载**不会减小安装包体积**（只是 UX 包装），别把它当卖点宣传成"省空间"。
2. 付费墙应该挂在**能力**上（提醒、多模板、备份、导入导出），不要挂在"安装数量"上——参考工程结论明确：**放弃"试用到期锁核心功能"**、界面禁用 VIP 角标/横幅，靠价值自然转化（1-2 元一次性买断，主锚点是"数据备份/迁移"这种隐形刚需）。

## 七、真正的护城河：AstroBox 双端协同（二期）

**痛点铁证**：腕上输入是所有手环应用的死穴（参考工程为此做了 233KB 的中文输入法，实测"补上手机端批量导入后竞争力 2.4 → 4.6"）。

**做法**（复用已有原型，成本可控）：

| 步骤 | 内容 |
|------|------|
| 1 | 按需恢复 `@system.interconnect`（**可选开启**：用户不启用则不常驻、不耗电） |
| 2 | 定义 EvBox 的同步作用域：`tools`（工具注册表）/ `reminders`（提醒项）/ `backup`（快照）——沿用守门人模型，手环侧决定读/写边界 |
| 3 | 手环侧保留通用容器与协议，**业务逻辑不放在手环** |
| 4 | 手机侧（AstroBox 插件）做「配置中心」：批量录入纪念日、导入 CSV/JSON、导出备份、跨设备迁移、数据看板 |
| 5 | 反脆弱：通道失败静默降级，本机功能完全不受影响 |

**收益**：从"手环上的小工具"升级为"手机配、手环用"的产品；插件生态本身也是分发渠道（米坛社区用户已经在用 AstroBox 装包）。

## 八、定位建议（三选一，推荐 A+B 合并）

| 定位 | 一句话 | 卖点 | 风险 |
|------|--------|------|------|
| **A 腕上提醒中心** | "到点就震你一下" | 触感是手环独占能力 | 后台耗电与机型差异，需要工程投入 |
| **B 纪念日 / 仪式感管家** | "把重要的日子戴在手上" | 有数据、有情感、可分享 | 竞品多（但腕上极简版少） |
| **C 个人数据小管家** | "腕上的记录本" | 数据资产 | 输入成本高，依赖 M4 |

**推荐**：**A + B 合并为「腕上的日子与提醒」**（倒数日/纪念日/生日/用药/打卡共一个内核），C 作为二期随能力生长。

> 候选 slogan：「重要的日子，戴在手上」/「抬腕即见，到点即震」/「EvBox：手腕上的提醒与纪念日」

## 九、路线图（含验收标准）

| 阶段 | 做什么 | 验收标准 |
|------|--------|---------|
| **P0 减负与聚焦（1 周）** | ① 开发工具（设备信息/ID 诊断/黑屏检测）移入「实验室」隐藏入口（参考工程做法：设置页标题连点 5 次）② 首页宫格改为注册表驱动 ③ 工具列表按"常用/实验室"分组 | 首页首屏不再出现开发项；`TOOLS` 硬编码消失 |
| **P1 一支点做深（2-3 周）** | 倒数日 → 纪念日管家：农历、重复规则、提前提醒、月历视图、二维码导入导出、多显示模板、钉首页大数字 | 单工具能力 ≥ 竞品手环版；能给自己发一张二维码并在新设备还原全部数据 |
| **P2 外壳与变现（1-2 周）** | 预置式工具市场（安装/停用/卸载/排序）+ 高级版能力墙重排（提醒/多模板/备份/导入导出） | 停用/恢复/彻底卸载三条路径数据行为正确；免费版功能完整可用（不锁核心） |
| **P3 护城河（3-4 周，可选）** | interconnect 按需开启 + 协议文档 + AstroBox 插件「EvBox 配置中心」（批量导入/导出/看板） | 手机端 100 条纪念日一键导入成功；关闭通道后手环功能无异常 |
| **P4 横向扩展（按需）** | 用同一内核派生：打卡 / 用药 / 喝水 / 经期模板 | 新增模板 ≤ 1 个页面 + 1 个模板配置，包体积增量 < 30KB |

## 十、风险与最小验证

| 风险 | 应对 |
|------|------|
| 提醒不准被骂 | 明确精度说明 + 打开补偿提醒；把"提前"设计成默认开启 |
| 后台耗电、部分机型不支持 | 事件窗口唤醒 + 提供"仅打开时提醒"降级档 |
| 农历数据体积 | 只内置 1900-2100 的压缩农历表（约几 KB），不上完整节日库 |
| 月历/图表触发单帧 200+ 节点红线 | 分帧挂载（参考工程实测：200+ → 70 节点） |
| 高级版被指"锁功能" | 参考工程教训：不做"试用到期锁核心"，不挂 VIP 角标 |
| 自嗨做了一堆没人用 | 每个新模板上线前先问三判据（随时可见？到点发生？积累数据？） |

**最便宜的方向验证实验（1 天内可完成）**：
1. 把倒数日加上「农历 + 重复规则 + 钉首页大数字」；
2. 在米坛发一贴，看**次周留存/评论诉求**是否明显好于现在的"工具箱合集"叙事；
3. 若评论开始问"能不能提醒我"，则 P1 的提醒方向成立，再投 P3。
