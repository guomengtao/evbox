## 1. 胶囊屏隐藏顶部三切换按钮

### 1.1 现状

`src/pages/index/index.ux` 的模式切换行 `.mode-row`（高 52px + `margin-bottom: 6px`）位于倒数日 Hero 与工具区之间，圆屏/方屏/胶囊屏**都显示**。

### 1.2 做法

只在胶囊/药丸屏隐藏，其余屏型保留：

```css
/* index.ux 的胶囊屏媒体查询内追加 */
@media (shape: capsule), (shape: pill-shaped) {
  .mode-row { display: none; }
}
```

### 1.3 收益（垂直空间）

| 项 | 数值 |
|---|---|
| 原占用 | `.mode-row` 52px + `margin-bottom` 6px = **58px** |
| 隐藏后 | 0 |
| 净释放 | **58px**（≈ 胶囊屏工具区一整行图标卡的高度） |

按 `doc/胶囊屏首页美化设计-三模式.md` 的预算，胶囊屏固定区块原合计 266px，隐藏后降到 **208px**，工具区余量从 164px 提升到 **222px**。

### 1.4 代价与兜底（必须做）

胶囊屏用户**无法在首页切换模式**，因此必须保证另有一条路：

- ✅ 已有：`pages/homepage-settings` 的「工具显示 → 图标/列表/图文」chip 组可切换（已实现并验证）
- 模式偏好本来就共用 `homepage_settings.toolViewMode`，两处读写同一份数据，**不会出现胶囊屏卡死在某个模式**的情况

> 提醒：胶囊屏隐藏后，`.tool-card` 仍是 2 列（`width: 48%`），不受影响。

## 4. 首页末位「退出」按钮

### 4.1 复用已有能力（不要重写）

`src/data/utils.js` 已经有现成的退出封装，**直接 require 使用**：

```js
var utils = require("../../data/utils.js")
// 逐个探测 exit / terminate / finish，返回是否调用成功
var ok = utils.exitApp()
```

它的注释已说明：不同快应用运行时暴露的退出入口不一致，返回 `true` **仅表示调用未抛异常**，不保证真退出（部分运行时会最小化）。

### 4.2 落地

`index.ux` 的 `TOOLS` 末尾追加（**必须是最后一条**）：

```js
{ id: "exit", name: "退出", iconFile: "tool_exit.png", exit: true }
```

`openTool()` 增加分支：

```js
openTool(item) {
  if (!item) return
  if (item.exit) {          // 退出不是跳转
    vibrator.vibrate({ mode: "short" })
    var ok = utils.exitApp()
    if (!ok) prompt.showToast({ message: "此设备不支持直接退出，请用手势返回表盘" })
    return
  }
  router.push({ uri: item.uri })
}
```

> 注意：模板里现在是 `onclick="openTool($item.uri)"`，要改成传整条 `onclick="openTool($item)"`，列表/图文模式同步改。

### 4.3 设计取舍

- **不做二次确认**：退出是可恢复操作（重开即可），而用户的痛点是"退不出去"，加确认会抵消这个价值
- **加短震 + 失败兜底提示**：点击有触感反馈；运行时不支持时明确告知用户改用系统手势
- 视觉上建议给退出项一点区分（如图标容器用 `border` 描边而非实底），降低误触概率——但**不要**靠颜色警告色，会破坏主题一致性

### 4.4 数量影响

加完后首页工具数为 **7 + 2 + 1(退出) = 10 个**：

| 屏型 | 图标模式列数 | 行数 |
|---|---|---|
| 胶囊 | 2 列 | 5 行（需滚动，已有 `scroll`） |
| 圆屏/方屏 | 4 列 | 3 行 |

### 5.6 移植时必须避开的坑（来自参考工程文档）

| 坑 | 正确做法 |
|---|---|
| 直接 `interconnect.onmessage = ...` **不生效** | 必须 `interconnect.instance()` 拿 `connect` 再挂回调 |
| 回调数据位置 | 在 **`data.data`**，不是 `data` |
| `connect.send` 的 `data` 参数 | 传 **Object**（框架序列化）；传字符串会双重转义。接收端对 string/object **双兼容** |
| ES6 可选链 `?.` | **禁用**，轻则报错重则整段脚本不执行白屏，一律 `var` + `&&` |
| 响应时延 | export 聚合多个异步读，最长约 2s，插件侧应等 **≥3s** |
| 错误码 | `1000` 未知 / `1001` 手机 App 未安装 / `1006` 连接断开 / `204` 超时；`getReadyState`：`1` 已连接、`2` 断开 |
| 无 msgId 配对 | 并发请求无法配对，回包靠 `action` 字段区分 |

### 5.7 resident 与耗电（必须给用户开关）

接收消息依赖 `system.resident` 后台常驻。参考工程是**强制常驻、无开关**，官方明确建议"至少在设置页给用户一个关闭选项"。

EvBox 的做法（与 `doc/EvBox差异化与方向规划.md:180` 一致）：

- 设置页新增「同步通道」开关，**默认关闭**
- 关闭时不 `startResident`、不建立通道 → 零耗电，其余功能完全不受影响
- 打开时才常驻；`onDestroy` **不**主动 `stopResident`（保持通道存活）

> 另需说明：手机端 AstroBox 插件（`.abp`，Rust→WASM）是**另一个独立工程**，不在本仓库。本设计只负责手环侧的收发接口；没有配套插件时，通道建不起来（属预期，不是 bug）。

## 6. 同步器聊天 / 留言表

### 6.1 能力边界（先说实话）

这是**异步留言**，不是微信式即时聊天。原因硬 constraint：

1. interconnect 通道只在**手环在线且 resident 常驻**时可用；手环息屏/切后台可能断连
2. 协议**没有 msgId / 请求-响应配对**，无法做"已读回执""正在输入"这类实时状态
3. 手环主动 `send` 的可靠性参考工程只给了提案（`docs/EV课程表主动发送测试消息到插件.md`），**未实测**

所以设计为**拉取 + 推送混合**：

- 插件 → 手环：`chat_push`（插件推，手环在线即收）
- 手环 → 插件：手环写入本地列表（`from:"device"`），插件下次 `chat_pull` 取走

真实体验：手机留言后，手环在下一次插件同步时看到；手环回复后，插件下次拉取时收到。**不要**在 UI 上做"对方正在输入""已读"等承诺。

### 6.2 数据结构

```js
// storage key: sync_chat_list
[
  { "id": "1695744000000", "from": "phone",  "text": "记得吃药", "ts": 1695744000000, "read": false },
  { "id": "1695744060000", "from": "device", "text": "收到",     "ts": 1695744060000, "read": true  }
]
```

- 上限 **200 条**，超出丢弃最旧的（手环存储与内存都紧）
- `from`：`"phone"`（同步器）/ `"device"`（本机）
- 未读红点：统计 `from === "phone" && !read` 的数量

### 6.3 手环端页面 `pages/sync-chat`

```
┌──────────────────────────┐
│ ‹  同步器留言        3未读 │  标题 26px
├──────────────────────────┤
│ 同步器                    │
│ 记得吃药                  │  气泡：对方 22px，lines: 3
│              09-26 21:30 │
│                          │
│                    我    │
│                  收到    │  气泡：本机 22px，右对齐
│              09-26 21:31 │
├──────────────────────────┤
│ [ 写留言 ]                │  主按钮 52px，走中文输入法
└──────────────────────────┘
```

- 路由注册到「设置与系统」组，`name_cn: "同步器留言"`
- 气泡文字 **22px**（底线），单条最多 3 行；文案超长就换行，**不省略**（§7）
- 「写留言」跳 `pages/chinese-input`（与昵称/倒数日同一条链路，已验证可用）
- 进入页面即把 `from:"phone"` 的全部标记 `read: true`

### 6.4 设置栏目入口

`pages/settings/settings.ux` 在「工具」行之后插入：

```html
<div class="row" onclick="openSyncChat">
  <text class="row-label">同步器留言</text>
  <text class="row-hint">{{ chatUnread > 0 ? chatUnread + ' 条未读' : '与同步器沟通' }}</text>
```

### 6.5 协议扩展

```js
// 插件拉取手环侧留言
{ action: "chat_pull", since: 1695744000000 }
→ { ok: true, action: "chat_pull", messages: [ /* from=device 的增量 */ ] }

// 插件推送留言到手环

→ { ok: true, action: "chat_push", count: 1 }
```

## 7. 项目要求新增：胶囊屏文字禁止省略

> 这条已同步写入 `doc/capsule-font-standard.md`（胶囊屏字号规范的正式章节），并在本文档作为硬约束执行。

### 7.1 规则条文

> **任何位置的文字都不允许被截断、省略、显示不全。**
> 空间不够时，按「缩短文案 → 换行 → 缩小字号（不低于 22px）→ 改布局」的顺序解决；
> **最后手段是换行或滚动查看，绝不是加省略号。**

### 7.2 位宽计算表（胶囊屏内容宽 160px）

按"中文字符宽 ≈ 字号 × 1.0"估算单行可容纳字数：

| 字号 | 单行可容字数 | 适用 |
|---|---|---|
| 22px | 7 字 | 最小底线：辅助说明、时间戳、摘要 |
| 24px | 6 字 | 标签、列表副标题 |
| 26px | 6 字 | 正文、气泡 |
| 28px | 5 字 | 列表主标题 |
| 30px | 5 字 | 页面标题 |
| 36px | 4 字 | 强调数字 |
| 40px | 4 字 | 答案之书大字 |
| 48px | 3 字 | Hero 大数字 |

> 圆屏/方屏按各自内容宽另算，但**规则一致**。

### 7.3 处理优先级（空间不够时严格按序）

1. **缩短文案**：改措辞，让它在预算内（首选）
2. **换行**：加大 `lines`（如 `lines: 2 / 3 / 4`），让文字自然折行
3. **缩小字号**：只能降到 **22px** 为止（低于 22px 汉字视角 <18 arcmin，不可读）
4. **改布局**：从单行改双行、从并排改上下、或给该区域更多高度
5. **滚动**：容器 `scroll-y` 让用户滑着看完整
6. ❌ **绝不允许**：`lines: 1` + `text-overflow: ellipsis` 去截断中文长文案

### 7.4 明令禁止与例外

**禁止：**

```css
.text { lines: 1; text-overflow: ellipsis; }   /* 中文长文案禁止这样 */
```

**例外（仅限以下）：**

- 单字/双字固定短标签（如倒数日的「钉」chip、单位「天」）
- 图标模式下的工具名——但前提是**名称 ≤3 字且已按卡片宽度算过**（现有 `TOOLS` 全部满足）
- 系统/平台层面无法控制的文本（极少）

### 7.5 验收方式

- 新增/修改任何页面后，逐屏核对每个 `<text>` 节点：把最长的一条真实数据填进去，确认**完整可见**
- 自查清单：搜索 `.ux` 里所有 `text-overflow: ellipsis`，逐条确认属于上述例外
