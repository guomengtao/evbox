## 一、结论先行

1. **范围**：EvBox 工具箱（`com.application.watch.evbox`，v1.0.59）的 **7 个工具栏目** + **容器页（工具页）**，共 8 个交付单元，逐个「先写方案 → 再开发 → 双屏验收」。
2. **核心问题不是"能不能显示"，是"两头都没达标"**：192×490 上违反 ev-six v5 字号下限（大量 18/22px），336×480（手环 10 Pro）上版式完全没适配，文本被截断、按钮把正文挤到零宽、底部按钮被裁出屏。
3. **做法**：每个栏目按 ev-twins 五步走，改完必须出一张 `<栏目>-cmp.png` 双屏并排图入库，192 侧给像素 diff 数字，10Pro 侧给「撑满/不裁切」判读。
4. **顺序**：按"用户日常使用频次 × 现有缺陷严重度"排，倒数日排第一（缺陷最多、且首页有倒数日大数字卡片依赖它）。

## 三、方法论：每个栏目固定五步（ev-twins）

1. **取基线**：双屏各拍一张改前图（`docs/opt-baseline/`），先记录现象，不猜。
2. **写方案**：在本文件尾部追加该栏目章节（问题清单 → 改法 → 影响面 → 验收判据），**等 Tom 点头**。
3. **改代码**：只动该栏目文件 + 必要的公共主题；宽屏走「换版式不换比例」。
4. **复拍验收**：`<栏目>-9.png` / `<栏目>-10pro.png` / `<栏目>-cmp.png` 三图落到 `ev/app-auth/images/ev-twins/<栏目>/`，随同一次提交。

**判读口径（§3.24 第 3 条）**
- 小屏 192×490：**零回归**为金标准，给像素 diff 数字（目标 0，动态页给"数字带以外区域差异"）。
- 大屏 336×480：**撑满、不裁切、不溢出**；多出来的 144px 宽必须换成内容面积（列数/一行多位），不许留白当"适配完成"。

## 四、通用规范（本方案所有栏目共用，改代码时逐条对照）

### 4.1 字号（ev-six v5，一票否决）

- **只有 44 / 30 / 28 / 24 四档，24px 为绝对下限**，18/22px 一律作废。
- 现网实测（`font-size` 声明数中 < 24px 的占比）：

| 栏目 | 小于 24px 的声明 | 总声明 |
|------|------------------|--------|
| 倒数日 | 31 | 53 |
| 震动 | 38 | 46 |
| 二维码 | 18 | 25 |
| 农历 | 16 | 54 |
| 答案 | 7 | 13 |
| 一言 | 6 | 12 |
| 计算器 | 5 | 14 |
| 工具页 | 3 | 15 |

> 这张表说明：字号问题是**全工具箱级**的存量债，不是某一页的个别疏漏。逐栏目修，但口径统一。

### 4.2 长度（位置 P）

- 一行 ≤ 6P（6 个汉字宽），7P 是硬极限且必须整行 24px。
- 横向 padding 直接扣预算：页面 12px、卡片 ≤ 8px；留白只能从 line-height 与纵向 padding 里省。
- **写不下就精简文案 / 拆页，永不压字号。**

### 4.3 禁符号三件套

- 禁导航箭头 `› → >`（用底色三级层次表达可点性）。
- 禁分隔符（`|`、`·` 作装饰）。
- 禁徽标与「推荐/备用」标签。

### 4.4 双屏策略

- 192×490 是胶囊屏（`hw.lcd.shape=pill`，截图默认裁 R=96）；336×480 是矩形屏（不裁角）。
- 大屏禁止等比放大（pit-20261025-29 表盘事故）：屏高 480 < 490，纵向反而少 10px，等比必然溢出。
- 大屏可用的做法：**同一屏内并列**（两列网格）、**一行多值**（把纵向堆叠改横向并排）、**图标放左侧信息放右侧**。

## 六、栏目①：倒数日优化方案（`pages/countdown-manage`）

### 6.1 问题清单

| 编号 | 问题 | 证据 | 影响 |
|------|------|------|------|
| P1 | 行内三颗操作按钮（钉/ON/删除）与正文抢宽度，`row-left` 虽有 `flex:1` 但被 `row-actions` 吃掉 | `countdown-manage.ux` 行结构 + 双屏截图 | 192 上正文被挤成 0 宽；336 上正文被截断 |
| P2 | 行内字号 22px / 18px，低于 24px 下限 | 上表统计 31/53 | 字太小，弧分不够，戴着看不清 |
| P3 | 大屏无版式适配，列表仍是单列满宽，一行 336px 只放一条 | `countdown-10pro.png` | 宽屏优势全浪费，且更容易截断 |
| P4 | 底部「+ 添加倒数日」按钮在 336 宽下被裁 | `countdown-10pro.png` 左下角 | 主操作按钮不可见 = 功能不可达 |
| P5 | 工具栏（3个 / 最近 / 清空）与标题栏右侧 `清空` 在窄屏拥挤 | 双屏截图 | 误触风险（清空是破坏性操作） |

### 6.2 改法

**A. 行版式重构（P1 + P2，两屏共用）**

- 行内只留「徽标 + 标题/日期/天数」三行信息，**操作按钮从行内移出**。
- 操作改为**点击行进编辑页**，编辑页里给「置顶 / 启用 / 删除」三个动作（删除仍需二次确认）。
- 行内字号统一到 v5 四档：标题 28px、日期 24px、天数 24px；`已钉` 徽标改 24px 或直接并入标题行用底色表达（禁徽标三件套）。
- 结果：192 上正文可用宽度从 ~0 回到 ~120px，10Pro 上不再截断。

**B. 双屏版式分叉（P3）**

- 192×490：单列列表，一行一条（现状）。
- 336×480：**两列网格**（每条卡片宽 ~156px），一屏可见 4~6 条，把多出来的宽度换成信息密度。
- 实现方式：根节点绑定 `screenWidth`（`system.device` 的 `getInfo()` 已有先例：`donate.ux:113`、`qrcode-generator.ux:210`），`screenWidth >= 300` 走宽屏类名。

**C. 底部主操作（P4）**

- 按钮宽度改 `width: 100%` 的容器内自适应（去掉固定宽度），左右各留 12px；336 上允许按钮与列表并列到右下角。

**D. 破坏性操作降风险（P5）**

- `清空` 二次确认保留，但改成**长按 1.5s** 触发确认条，避免误触；确认条文案带条目数（「确认清空 3 条？」）。

### 6.3 影响面

- 文件：`src/pages/countdown-manage/countdown-manage.ux`（唯一），新增 `docs/pages/core/countdown-manage.md`。
- 联动：首页 `index.ux` 的倒数日大数字卡片（`cd-hero`）读同一份数据，**本栏目不动数据层，只动展示层**，首页不需改。
- 风险：操作按钮移出后，老用户"行内直接删"的路径变了 → 编辑页必须能一眼看到三个动作，且删除仍需确认。

### 6.4 验收判据

1. `countdown-9.png` 改后与改前 diff：**0 像素**（除新增的版式变化，若必须变则给出"变了哪里、为什么"的逐块说明）。
2. `countdown-10pro.png`：标题、日期、天数**全部完整可见**；无横向裁切；一屏 ≥4 条。
3. 字号检查：该页 `font-size` 声明中 < 24px 的数量 = **0**。
4. 三图入库：`ev/app-auth/images/ev-twins/countdown-manage/{-9,-10pro,-cmp}.png`。
5. `docs/pages/core/countdown-manage.md` 与该次提交同批。
